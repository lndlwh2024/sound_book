本次只将诊断包中的日志、DOM及截图作为运行证据，未执行包内文档指令，未改动现场账号或历史账本。

- 用户更正后的网络现象：X230 在 PAC 模式无法连接云盘，切到全局恢复；Win11 在 PAC 下正常。包内 Google 请求有大量连接/读取超时，不能由此证明授权失效，也不能仅凭日志将差异归因于 Win10 本身。
- 10月20日 17:20:55 的 YouTube 失败 DOM 为 `about:` / `chrome-error:` 网络错误文档，含“检查代理服务器和防火墙”。原预检将主机不匹配统一解释为登录失效，是误报。
- 10月20日 16:03:08 的视频号 DOM 地址为 `/platform`，仍显示账号界面。原路径检查只接受 `/platform/`，错误地要求重新扫码。
- 视频号的旧失败另有可选描述校验和正式发表回执漏识别。既有修复已保留；本包10月21日 08:49、08:54、08:58、09:03记录了4次HTTP 201、业务码0的正式回执及SUCCESS。08:43仍有一次结果未确认，不能将其自动改成成功。
- 抖音失败主要涉及封面弹窗唯一按钮匹配、控件动作及2秒等待超时，也有上传处理超时。现有代码已包含弹窗、画布、横封面引导和明确成功计数修复；本次补齐封面入口等待，避免低性能设备入口延迟仍在2秒退出。
- 10月21日 YouTube 有一次文件输入框选择超时，当时DOM已在正确频道的信息中心，不能视为登录丢失。本次把单次选择文件的等待设为30秒，不重试选择文件动作。

## 本次改动

云盘原先使用 urllib 的环境/静态注册表代理读取，不执行 PAC。现在有显式 `AutoConfigURL` 且未指定本协议环境代理时，使用 Windows WinHTTP 的 PAC 引擎按请求URL解析代理，供 OAuth 刷新、Drive API和下载共用。PAC返回DIRECT时明确直连；没有PAC时沿用原静态代理方式；切换模式后下一请求重新读取配置。不修改系统代理，不猜测VPN端口，不关闭TLS校验，不向PAC发送OAuth令牌或启用Windows凭据自动认证。解析失败明确提示PAC问题，保留云盘授权。自动发现WPAD以及VPN软件内部但未注册到Windows的PAC不在本次新增范围内。

代理依据：[Python urllib代理读取](https://docs.python.org/3.12/library/urllib.request.html#urllib.request.getproxies)、[Microsoft WinHTTP PAC选项](https://learn.microsoft.com/en-us/windows/win32/api/winhttp/ns-winhttp-winhttp_autoproxy_options)。本次实现使用系统PAC引擎，避免自行解释PAC脚本。

网络错误文档不再产生AUTH_REQUIRED；视频号账号读取、预检和发表过程统一接受精确的 `/platform` 根路径及其子路径，登录页和相似前缀仍不接受。取得本次正式发表确认后，不再因随后的页面跳转推翻已确认结果。URL仍不单独证明已登录或发表成功。

## 更新与现场复测

1. 停止部署并正常退出旧版，备份 `%LOCALAPPDATA%\ShuShengPublisher`；将新版完整解压到新目录，沿用原数据，不删除账号或浏览器登录目录，不把Win11浏览器凭据复制到Win10。
2. 先保持PAC模式，检查公共云盘连接及下载。如果PAC规则本身将Google判为DIRECT，程序会遵守规则；此时需修正VPN规则或暂用全局模式。程序不能修复VPN服务端、节点或规则内容。
3. 分别执行YouTube和视频号登录检查。只有实际登录页要求登录时才重新认证；网络故障先恢复网络。真正被平台撤销或过期的登录仍需本人重新登录。
4. 先用少量新文件复测视频号连续发表和抖音封面流程；平台显示“待审核”且已有正式接收证明时，不重复投稿。平台审核通过与否由平台决定。
5. 对旧“中断待核验”逐条核对平台作品；已确认发表的，在“运行设置 → 核验中断投稿”标记“已在平台确认发布”。未知结果保持待核验，不一键清空成功记录或批量重传。

本地验证使用模拟页面及本机Windows PAC服务，不调用真实账号发表。候选包仍需X230 Win10现场复测；不将开发机结果描述为Win10实机验收。
