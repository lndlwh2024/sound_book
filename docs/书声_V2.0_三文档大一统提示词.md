# 一、产品正式名称

产品名称：

**书声**

内部英文名称可以使用：

`ShuSheng`

产品定位：

> 将 PDF / EPUB 等电子书，通过自动化处理生成带旁白、字幕、背景音乐、封面、主标题和自动副标题的分集 MP4 有声视频。

书声同时保留底层的有声书生成能力。

书声不是：

- 视频剪辑软件；
- 剪映仿制品；
- 单纯 TTS 小工具；
- 依赖 LLM 临场决策的 Agent 工作流。

核心生产流程应当是：

**确定性的 Python Pipeline + 可替换的 TTS / 字幕 / 音视频处理模块。**

# 六、本地 TTS 模型首次选择时必须自动初始化

这是书声的正式产品能力。

当用户第一次选择某个本地 TTS 引擎，例如：

`F5-TTS`

而当前电脑尚未完整部署该模型时：

**不得立即开始下载模型。**

必须按照下面顺序执行。

## 6.1 第一步：检查是否已经部署

检查：

- Runtime 是否存在
- Backend 是否安装
- 模型是否存在
- 模型核心文件是否完整

如果全部正常：

直接：

`READY`

## 6.2 第二步：未部署时先检查硬件

至少检查：

- 操作系统
- CPU 架构
- 系统 RAM
- GPU
- GPU VRAM
- CUDA 是否可用
- Torch / CUDA 兼容性
- 可用磁盘空间

然后根据 Backend 声明的要求判断：

- 满足最低要求
- 低于推荐要求但可以运行
- 不满足最低要求

## 6.3 必须区分最低配置和推荐配置

不能把：

`低于推荐配置`

简单等价为：

`无法运行`

状态至少分：

### READY

满足正常要求。

### WARNING

低于推荐配置，但仍允许运行。

例如：

4GB VRAM 的设备仍可能运行 F5-TTS，只是：

- 较慢
- 需要低显存模式
- 可能使用 CPU fallback

这种情况下：

允许继续。

### BLOCKED

确实无法运行。

只有 BLOCKED 才禁止继续部署。

## 6.4 硬件不满足时禁止先下载

如果检测结果：

`BLOCKED`

GUI 必须明确显示原因。

例如：

当前设备不满足 F5-TTS 最低运行条件。

并停止初始化。

此时：

**禁止先下载几个 GB 的模型然后再告诉用户无法运行。**

## 6.5 检查磁盘空间

硬件通过后：

再检查模型和运行环境需要的磁盘空间。

如果空间不足：

显示：

- 预计需要多少空间
- 当前可用多少空间

然后停止。

不开始下载。

# 十三、分集规划分两阶段

## 13.1 TTS 前

- 章节字数

计算：

形成：

最终 Episode 分组。

# 十四、本次运行方式

单集目标时长与本次运行上限必须完全分开。

GUI 提供三种运行方式。

## 模式 A：全书

`一直处理到全书完成`

适合用户愿意让电脑长期运行。

## 模式 B：下一集

`本次只生成下一集`

生成一个完整 Episode 后：

安全停止。

## 模式 C：本次运行上限

例如：

单集目标：

30 分钟

本次运行上限：

60 分钟

书声尽量生成约 60 分钟成品。

例如：

两集。

然后在完整 Episode 边界：

自动安全停止。

不能为了严格满足 60:00：

切断章节或 Episode。

# 十五、长任务必须支持安全暂停

3. 当前正在处理的小单元正常结束

5. 保存 Manifest
6. 保存 Task State
7. 保存恢复位置

# 二十一、背景音乐自动处理

用户选择 BGM 后：

书声自动处理：

1. BGM 不够长时自动循环
2. 自动裁剪到当前 Episode 长度
3. 根据用户设置的 BGM 音量作为基准
4. 有旁白时进一步降低 BGM
5. 旁白较长停顿时允许 BGM 稍微恢复
6. 片尾自动淡出

普通 GUI 不需要展示：

`sidechaincompress`

`Ducking`

等专业词。

> “说话时自动降低背景音乐，保证旁白清晰。”

# 二十四、字幕处理原则

字幕正式主流程：

**不重新对 TTS 音频做一遍 ASR，再把识别结果当字幕。**

因为书声本来已经知道正确原文。

书声需要解决的问题只有：

> 原文中的每句话，从第几秒开始，到第几秒结束。

即：

电子书原文  
+  
书声生成的音频  
↓  
计算时间  
↓  
字幕

字幕文字必须以电子书原文为准。

这样减少：

- 人名识别错误
- 地名识别错误
- 专有名词错误
- 同音字错误

# 二十九、本地模型 Worker

F5 / Kokoro 不得：

每处理一个 Chunk 都启动一次 Python 并重新加载模型。

采用：

**Task-scoped Persistent Worker**

即：

一次 TTS Run 开始  
↓  
启动 Worker  
↓  
模型加载一次  
↓  
连续处理多个 Chunk  
↓  
本次 Run 完成 / 用户暂停 / 全书完成  
↓  
Worker 正常退出

Worker 不是永久 Windows Service。

# 三十、Worker 通信

建议：

`stdin / stdout + JSON Lines`

不要引入：

- HTTP Server
- Redis
- RabbitMQ
- Celery
- Windows Service

除非后续明确有新的架构需求。

# 三十一、Worker 崩溃恢复

如果：

Chunk 1 SUCCESS  
Chunk 2 SUCCESS  
Chunk 3 时 Worker 崩溃

则：

- Chunk 1 不重做
- Chunk 2 不重做
- Chunk 3 标记失败 / 待重试
- 主程序可以重新启动 Worker
- 模型重新加载
- 从 Chunk 3 继续

不能从一本书开头重新开始。

# 三十二、book_id

内部稳定标识：

`book_id = SHA256(source_file_content)[:16]`

用户：

不输入  
不查看  
不理解

另外保存：

- original_filename
- display_name

例如：

原始文件：

`人类简史（中文版）.pdf`

display_name：

`人类简史（中文版）`

book_id：

只用于内部。

如果用户只修改文件名：

内容没变，

book_id 应保持相同。

# 三十三、Cache / Fingerprint

TTS 音频必须支持缓存。

Fingerprint 至少包含：

- text_hash
- engine
- voice_profile
- speed
- 其他会影响声音结果的 options

只有：

fingerprint 一致

并且：

文件存在  
Audio QC 通过

才能复用旧结果。

# 三十四、Manifest

每完成一个成功的最小处理单元：

及时保存 Manifest。

保存方式必须安全。

建议：

- 写临时文件
- flush
- atomic replace

程序异常退出：

不能轻易损坏整个任务状态。

# 三十五、Audio QC

生成的语音至少检查：

- 文件存在
- 文件大小 > 0
- duration > 0
- FFmpeg 可读取
- sample rate
- channel
- 是否出现异常全静音

只有通过 Audio QC：

才进入后续流程。
